DESCRIPTION

Présentation générale et positionnement professionnel de Git

Git est un système de gestion de versions distribué qui permet de suivre l’évolution d’un projet logiciel dans le temps et de coordonner le travail de plusieurs développeurs sur le même code source. Il offre la possibilité de revenir à tout état antérieur du projet, de comparer des versions et de travailler sur plusieurs branches sans risquer de perdre ou de corrompre le code.

Dans un contexte professionnel, Git est devenu un outil incontournable du développement logiciel moderne. Il structure les processus de travail collaboratif, facilite la revue de code et garantit la traçabilité des contributions. Dans les environnements agiles et DevOps, il s’intègre directement aux chaînes d’intégration et de déploiement continus (CI/CD), permettant de livrer rapidement du code fiable et testé.

Les plateformes comme GitHub, GitLab et Bitbucket se sont imposées comme des standards dans les entreprises. Elles ajoutent à Git des fonctionnalités de gestion de projet, d’automatisation et de sécurité, renforçant la collaboration entre les équipes de développement, de test et d’exploitation. Cette évolution s’inscrit pleinement dans la tendance actuelle des pratiques de développement collaboratif et cloud-native adoptées par la majorité des organisations technologiques.

J’ai découvert Git dès ma Licence en Informatique, puis approfondi son utilisation durant mon Master en Ingénierie Logicielle à l’ISCOD. Au fil de mes stages, de mon alternance et dans mon poste actuel chez Dekra Automotive Solutions, Git est devenu un outil quotidien, au cœur du processus de développement collaboratif. Il m’a permis d’apprendre à structurer le travail en équipe, à gérer efficacement les branches de fonctionnalités, à résoudre les conflits de fusion et à maintenir un historique de code propre et traçable. Ces expériences ont fait de Git un réflexe naturel dans ma pratique de développement professionnel.

Aujourd’hui, Git constitue un pilier essentiel de mon profil de développeur full stack. Il me permet d’assurer la cohérence du code, la qualité des livrables et la fluidité des échanges au sein d’équipes de développement distribuées. Dans un environnement où la collaboration continue et la livraison rapide sont devenues des standards, la maîtrise de Git représente une compétence fondamentale et durable dans mon parcours professionnel.

UTILISATION DÉTAILLÉE

Pratiques, outils et intégrations concrètes

J’utilise Git de manière quotidienne, aussi bien dans mes projets académiques que professionnels. Que ce soit pour des travaux d’équipe, des projets personnels ou dans le cadre de mon poste actuel chez Dekra Automotive Solutions, Git est au cœur de ma pratique de développeur full stack.

Au sein de Dekra, j’emploie Git dans les pipelines de développement hébergés sur Azure DevOps. J’y pratique un Git workflow structuré basé sur les branches main, develop et feature/*, avec gestion des pull requests et validation par revue de code. Les commits atomiques et les messages conventionnels (type “Conventional Commits”) permettent de maintenir un historique clair, facilitant le suivi des évolutions et la génération automatique des versions. J’utilise également les commandes rebase, stash et cherry-pick pour gérer efficacement les contributions et résoudre les conflits de manière propre.

Sur le plan académique, j’ai eu l’opportunité de concevoir et mettre en place un Git workflow complet dans un projet d’équipe à l’ISCOD. Ce projet, développé en Spring Boot, s’appuyait sur une organisation rigoureuse des branches (develop, feature, release, hotfix) et sur l’utilisation de GitHub Actions pour automatiser les tests unitaires et le déploiement. Ce pipeline CI/CD reposait sur des fichiers .yml configurés dans le dépôt GitHub, permettant d’exécuter des builds et de déployer les artefacts après chaque merge validé.

J’ai également utilisé Git dans le cadre de mon projet de TER (Travail d’Étude et de Recherche), mené en équipe de cinq personnes. Nous avons mis en place un système de branches parallèles pour chaque membre, avec intégration régulière sur la branche principale. Les pull requests servaient à valider le code après relecture, et des tags étaient utilisés pour marquer les versions stables. Cette expérience a renforcé ma compréhension du travail collaboratif en environnement distribué et de la rigueur nécessaire à la gestion de version partagée.

En dehors des projets d’équipe, j’utilise Git également pour mes projets personnels hébergés sur GitHub, où je maintiens plusieurs dépôts actifs. J’y applique une gestion rigoureuse des commits, des branches et des releases, tout en utilisant des fonctionnalités avancées comme les issues, labels et projets Kanban pour suivre l’avancement des développements.

Mon utilisation de Git couvre l’ensemble du cycle de vie d’un projet : initialisation du dépôt (git init), clonage, gestion des remotes, création de branches, merge et rebase, gestion des conflicts, et déploiement automatisé via GitHub Actions ou Azure Pipelines. Ces pratiques garantissent une traçabilité complète du code et une intégration fluide dans les processus d’intégration continue.

ANECDOTES ET EXPÉRIENCES CONCRÈTES

Mise en œuvre de Git dans des contextes collaboratifs et professionnels

1. Mise en place d’un Git workflow complet lors d’un projet intensif en binôme à l’ISCOD

Lors d’un projet intensif d’une journée, organisé sous forme d’examen pratique dans le cadre de mon Master en Ingénierie Logicielle à l’ISCOD, nous travaillions en binôme sur le développement d’une application Spring Boot intégrant plusieurs modules fonctionnels. Le rythme soutenu et les contributions simultanées ont rapidement généré des conflits de fusion et des difficultés de coordination du code.

Au cours du projet, un bug critique a été introduit après que mon binôme ait poussé du code directement sur la branche main sans passer par la branche de développement. Ce commit non validé a cassé la compilation et rendu l’application inutilisable. Pour corriger la situation, j’ai identifié le commit fautif à l’aide des commandes git log et git diff, puis j’ai restauré une version stable via git revert. J’ai ensuite appliqué un correctif dans une branche dédiée à la correction de bugs, nommée hotfix/*, avant de la fusionner proprement dans develop et main.

Pour éviter que la situation ne se reproduise, j’ai mis en place un Git workflow simplifié inspiré de GitFlow, structuré autour des branches main, develop, feature/* et hotfix/*. Chaque modification devait désormais passer par une pull request avant validation, avec des commits atomiques et descriptifs. Cette organisation a permis de sécuriser les livrables et de conserver un historique clair et stable.

Malgré le temps limité, nous avons pu livrer une application fonctionnelle, stable et bien versionnée dans les délais. Cette expérience m’a appris à gérer un incident Git en temps réel et à appliquer les bonnes pratiques de workflow, notamment l’usage de branches hotfix pour les correctifs urgents et la protection de la branche main.

2. Adaptation à un changement client et rollback de fonctionnalité sur Azure DevOps chez Dekra

Dans mon rôle de développeur full stack chez Dekra Automotive Solutions, j’utilise quotidiennement Git via Azure DevOps pour la gestion du code source et la coordination des déploiements en environnement agile. Lors d’une phase de préparation de release, j’ai été confronté à un changement de dernière minute de la part du client, qui a impacté directement le plan de livraison.

Une nouvelle fonctionnalité SQL que j’avais développée — un flux automatisé de traitement et de reporting — était prête, testée et déjà fusionnée dans la branche main pour être déployée en production. Cependant, à la veille de la mise en ligne, le client a décidé de reporter sa mise en service à la prochaine release, le temps d’ajuster certains prérequis métiers. Cette décision impliquait de retirer le module du package de déploiement sans perturber les autres fonctionnalités validées.

Pour répondre à cette contrainte, j’ai effectué un rollback contrôlé sur les commits liés à cette fonctionnalité, à l’aide des commandes git revert et git log. J’ai ensuite créé une branche isolée pour y conserver le développement initial, afin qu’il puisse être finalisé et testé séparément avant d’être livré lors du sprint suivant. Cette approche a permis de préserver la stabilité du code en production tout en évitant la perte du travail effectué.

Cette situation m’a permis de mettre en pratique ma connaissance des stratégies Git avancées dans un contexte de livraison réelle. J’y ai renforcé ma compréhension de la gestion des versions différées et des demandes de changement client, tout en soulignant l’importance d’une communication fluide entre équipes de développement, test et pilotage projet. Elle illustre ma capacité à réagir rapidement et proprement face à des imprévus tout en maintenant un historique Git propre et maîtrisé.

NIVEAU DE MAÎTRISE ET CONTEXTUALISATION

Positionnement, progression et recul professionnel

Mon niveau sur Git est avancé. C’est un outil que j’utilise au quotidien, aussi bien dans mes projets professionnels que dans mes travaux académiques ou personnels. Je gère couramment les branches de fonctionnalités, les fusions, les rollbacks ou encore les rebase, et j’adapte le workflow selon le contexte du projet ou la taille de l’équipe.

Avec le temps, j’ai appris à faire de Git bien plus qu’un simple outil de versioning : c’est un véritable support d’organisation et de collaboration. J’accorde une attention particulière à la clarté des messages de commit, à la structure du dépôt et au respect des conventions d’équipe, car une bonne discipline Git simplifie tout — de la relecture à la maintenance du projet.

L’une des forces que j’ai développées est la mise en place de revues de code efficaces via les pull requests. Ces pratiques permettent de valider les changements avant intégration, de repérer rapidement les erreurs et d’éviter qu’une fonctionnalité incomplète ou instable ne soit livrée en production. C’est un réflexe que j’applique systématiquement dans mes projets collaboratifs.

Je continue à progresser sur les aspects plus techniques : automatiser les workflows avec les pipelines CI/CD, gérer des sous-modules dans des projets complexes et tirer parti d’outils comme Azure DevOps ou GitHub Actions pour fiabiliser le cycle de déploiement. Ces compétences s’inscrivent dans ma démarche d’évolution vers une meilleure intégration des pratiques DevOps.

Git est devenu pour moi un réflexe professionnel autant qu’un outil de qualité. Il garantit la stabilité du code, fluidifie le travail en équipe et renforce la confiance dans chaque livraison. C’est l’un des piliers de ma pratique de développeur full stack.

⚡ VITESSE D’ACQUISITION

Apprentissage progressif et consolidation par la pratique

J’ai appris Git principalement par la pratique, en travaillant sur des projets variés — aussi bien en équipe qu’en autonomie. Au fil du temps, j’ai cherché à comprendre ce qui se passait “sous le capot” : comment Git gère les branches, les fusions ou les retours en arrière, plutôt que d’appliquer des commandes sans en saisir le sens. Cette approche m’a permis d’en tirer une vraie maîtrise plutôt qu’une simple utilisation.

Je me suis appuyé sur la documentation officielle de Git et sur des ressources en ligne pour approfondir ma compréhension des workflows modernes. L’utilisation d’outils comme Sourcetree et l’intégration Git de Visual Studio Code m’a aussi beaucoup aidé à visualiser les relations entre commits, branches et merges, facilitant l’assimilation des concepts plus abstraits.

Une chose essentielle que Git m’a apprise, c’est qu’il ne faut pas avoir peur de se tromper. Chaque erreur est rattrapable : un revert, un reset ou un cherry-pick peuvent corriger une mauvaise manipulation. Cette liberté d’expérimenter sans crainte m’a permis d’apprendre vite et de devenir à l’aise avec les situations complexes.

Ma maîtrise de Git repose sur cette combinaison : la compréhension de ses mécanismes internes et une pratique constante sur des projets réels. C’est une compétence que je continue à affiner à travers la veille, l’expérimentation de nouveaux workflows et l’intégration dans des contextes d’équipe exigeants.
